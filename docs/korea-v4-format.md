# 대한민국 경계 v4 형식과 좌표 변환 규약

이 문서는 대한민국 좌표 변환에 사용하는 v4 경계 파일, 포함 판정, 등면적 후보 생성 및 보조 난수 소비 규약을 설명한다. 바이트 형식은 [생성기](../tools/build_korea_boundary.py), [패커](../tools/pack_korea_boundary.py), [Rust 판정기](../src/korea_boundary.rs), [웹 판정기](../korea_boundary.js)를 기준으로 한다. 배포 파일의 실제 개수·크기·해시는 [manifest](../data/korea-boundary-v4/manifest.json), 원본 경계의 보정 내역은 [boundary-validation.json](../data/korea-boundary-v4/boundary-validation.json)에 기록한다.

## 1. 원본과 현재 배포 자료

입력은 기존 보정 결과인 `land_mask_5179.shp`이며, SHA-256은 다음과 같다.

```text
5060f88241e2d80b87f052b4b83296ef59cd7f4ee066a9330bc2ea580bc55428
```

생성기는 입력 SHP의 해시와 EPSG:5179 좌표계를 확인한 뒤 `always_xy=True`로 EPSG:4326에 한 번 변환한다. 판정 대상은 이 변환으로 얻은 위경도 직선 선분의 폴리곤이다. 외곽선, 구멍, 분리 성분, 보정 국경 및 기존 물 영역 포함 정책을 그대로 사용한다. 투영 변환 이후의 정점을 단순화·반올림·클리핑하지 않는다. [원본 로딩과 생성](../tools/build_korea_boundary.py)

현재 배포 자료의 프로필은 다음과 같다. 개수는 형식 전체에 고정된 상수가 아니라 이 원본과 생성 설정의 결과다.

현재 `index.bin`의 SHA-256은 다음과 같다. Rust의 생성된 [데이터 모듈](../src/korea_boundary/data.rs)과 웹 모듈이 이 값을 고정한다.

```text
8cb20a5c0da9c3d6225efb0323e24a4f992eb3029a772da3a71a55d3f503bf17
```

현재 웹 배포는 `korea_boundary.js?v=4.1`과 `data/korea-boundary-v4/`를 함께 사용한다. 후속 최적화는 Rust 압축 해제·SHA-256과 웹의 짧은 허프먼 코드 조회 경로에 적용한다. 웹 모듈의 변경에 맞춰 모듈 캐시 식별자를 갱신했으며, 경계 파일은 최초 v4와 같은 바이트를 유지한다. [후속 성능 측정](korea-v4-performance-accepted-js-20261029.md)

추가 Rust 최적화는 경계 데이터의 SHA-256 검증에서 SHA 명령을 지원하는 x86_64 CPU에 전용 라운드 연산을 적용한다. 런타임 기능 감지를 통과한 경우에만 해당 경로를 호출하며, 다른 CPU는 기존 계산을 사용한다. 파일 인코딩, 정점 비트, 누적 면적 수학, 보완 난수 소비 및 캐시 예산을 유지하며, 웹은 기존 quick9 모듈을 사용한다. [추가 좌표 생성 성능 측정](korea-v4-coordinate-performance-20261029.md)

## 2. 기본 인코딩과 번호 체계

컨테이너의 정수 필드는 별도 표시가 없으면 little-endian `u32`다. 좌표는 little-endian IEEE-754 binary64다. SHA-256 필드는 64자리 문자열이 아닌 원시 32바이트이며, 매직은 ASCII 8바이트다. zlib 스트림 내부의 인코딩과 Adler-32는 zlib 자체 규약을 따른다.

타일 번호는 `row * columns + column`이며, 남쪽 행부터 북쪽으로, 각 행에서는 서쪽 열부터 동쪽으로 증가한다. 페이지 번호는 전체 자료에서 연속된 전역 번호다. 한 타일의 페이지가 조각 파일 경계를 넘어갈 수 있다. 조각 파일은 번호를 최소 세 자리로 0 채움한 `part-000.bin`, `part-001.bin` 등의 이름을 사용한다. [패커](../tools/pack_korea_boundary.py)

## 3. 루트 인덱스: `index.bin`

전체 배치는 다음과 같다.

```text
128바이트 헤더
tile_count × 12바이트 타일 레코드
part_count × 48바이트 조각 레코드
파일 끝
```

파일 길이는 정확히 `128 + tile_count * 12 + part_count * 48`이어야 한다. 별도 패딩이나 뒤따르는 자료는 없다.

### 3.1 루트 헤더

| 오프셋 | 바이트 수 | 내용 |
| ---: | ---: | --- |
| 0 | 8 | `SRGKR004` |
| 8 | 4 | 헤더 길이, 128 |
| 12 | 4 | 타일 수 |
| 16 | 4 | 조각 수 |
| 20 | 4 | 전체 페이지 수 |
| 24 | 4 | 폴리곤 성분 수 |
| 28 | 4 | 링 수 |
| 32 | 4 | 닫힘 정점을 포함한 원본 정점 수 |
| 36 | 4 | 열 수 |
| 40 | 4 | 행 수 |
| 44 | 4 | 도당 셀 수 `scale` |
| 48 | 8 | 격자 서쪽 원점 `grid_west`, f64 |
| 56 | 8 | 격자 남쪽 원점 `grid_south`, f64 |
| 64 | 8 | 마스크 `west`, f64 |
| 72 | 8 | 마스크 `south`, f64 |
| 80 | 8 | 마스크 `east`, f64 |
| 88 | 8 | 마스크 `north`, f64 |
| 96 | 32 | 보정 SHP의 SHA-256 |

### 3.2 타일 레코드

타일 `t`의 레코드는 `128 + 12*t`에서 시작한다.

| 레코드 내 오프셋 | 바이트 수 | 내용 |
| ---: | ---: | --- |
| 0 | 4 | 상태: 0=`OUTSIDE`, 1=`INSIDE`, 2=`MIXED` |
| 4 | 4 | 첫 전역 페이지 번호 |
| 8 | 4 | 페이지 수 |

`MIXED` 타일만 양수의 페이지 수를 갖는다. `OUTSIDE`와 `INSIDE`의 페이지 수는 0이다. 페이지가 없는 타일도 첫 페이지 필드에는 앞 타일까지의 누적 페이지 수를 기록한다. 타일 레코드를 순서대로 읽었을 때 모든 페이지 구간이 빈틈과 중복 없이 이어지고, 마지막 누적값은 헤더의 전체 페이지 수와 같아야 한다.

### 3.3 조각 레코드

조각 레코드 영역은 `128 + tile_count*12`에서 시작한다.

| 레코드 내 오프셋 | 바이트 수 | 내용 |
| ---: | ---: | --- |
| 0 | 4 | 조각의 첫 전역 페이지 번호 |
| 4 | 4 | 조각의 페이지 수 |
| 8 | 4 | 조각 파일의 정확한 바이트 길이 |
| 12 | 4 | 예약 필드, 0 |
| 16 | 32 | 조각 파일 전체의 SHA-256 |

조각의 페이지 구간도 연속된다. 각 조각은 페이지를 적어도 하나 포함하며, 전체 조각을 합친 페이지 수는 헤더와 일치한다. Rust는 조각 수를 컴파일에 포함된 `PARTS` 개수와도 대조한다. [루트 파서](../src/korea_boundary.rs)

## 4. 조각 파일: `part-NNN.bin`

전체 배치는 다음과 같다.

```text
64바이트 헤더
해당 조각의 page_count × 12바이트 페이지 레코드
페이지별 독립 zlib 스트림을 순서대로 연결
파일 끝
```

### 4.1 조각 헤더

| 오프셋 | 바이트 수 | 내용 |
| ---: | ---: | --- |
| 0 | 8 | `SRGKP004` |
| 8 | 4 | 첫 전역 페이지 번호 |
| 12 | 4 | 페이지 수 |
| 16 | 4 | 조각 파일 전체의 정확한 바이트 길이 |
| 20 | 4 | 예약 필드, 0 |
| 24 | 32 | 루트와 같은 보정 SHP SHA-256 |
| 56 | 8 | 예약 `u64`, 0 |

### 4.2 페이지 레코드

| 레코드 내 오프셋 | 바이트 수 | 내용 |
| ---: | ---: | --- |
| 0 | 4 | 조각 파일 시작을 기준으로 한 압축 스트림 오프셋 |
| 4 | 4 | 압축 스트림 바이트 길이 |
| 8 | 4 | 압축 해제한 페이지의 정확한 바이트 길이 |

첫 압축 스트림은 `64 + page_count*12`에서 시작한다. 이후 스트림은 앞 스트림의 끝에서 곧바로 이어진다. 길이가 0인 스트림, 구간 사이의 빈틈, 파일 밖으로 나가는 구간 및 마지막 스트림 뒤의 잔여 바이트는 오류다. 각 스트림은 zlib 헤더·DEFLATE 자료·Adler-32를 갖는다. 조각 SHA-256과 스트림의 압축 체크섬, 해제 길이를 각각 확인한다. [조각 생성](../tools/pack_korea_boundary.py), [Rust 압축 해제](../src/boundary_inflate.rs)

### 4.3 현재 생성기의 조각 배치

현재 생성기는 헤더·페이지 레코드·압축 스트림을 합쳐 조각당 524,288바이트 이하로 만든다. 독립 압축 페이지를 생성 순서대로 담고, 다음 페이지를 추가하면 상한을 넘을 때 현재 조각을 끝낸다. 여러 타일은 같은 조각을 공유할 수 있으며, 한 타일의 페이지가 조각 경계를 넘어갈 수도 있다. 이 배치는 정점, 원본 선분, 페이지 번호 및 페이지 안의 기하를 바꾸지 않는다.

생성기의 512 KiB 조각 상한은 현재 런타임 파서의 형식상 상한과 같다. 페이지 압축·복원 규약과 포함 판정은 조각 배치와 독립적이다. 배치를 바꾸면 루트의 조각 레코드와 각 조각 해시가 바뀌므로 생성된 Rust 데이터 모듈과 웹의 고정 루트 SHA-256도 함께 갱신해야 한다. 64 KiB로 재배치한 후보는 HTTP 응답 지연을 준 비교에서 회귀가 확인되어 최종 구성에 포함하지 않는다. [패커](../tools/pack_korea_boundary.py), [후속 성능 측정](korea-v4-performance-accepted-js-20261029.md)

## 5. 압축 해제한 페이지

모든 페이지는 다음 공통 헤더로 시작한다.

| 오프셋 | 바이트 수 | 내용 |
| ---: | ---: | --- |
| 0 | 8 | `SRGKB004` |
| 8 | 4 | 소유 타일 번호 |
| 12 | 4 | 전역 페이지 번호 |
| 16 | 4 | 종류: 0=원거리 교차 패리티, 1=원본 링 체인 |
| 20 | 4 | 종류 0에서는 이벤트 수, 종류 1에서는 선분 수 |
| 24 | 4 | 종류 0에서는 시작 패리티, 종류 1에서는 링 번호 |
| 28 | 4 | 종류 0에서는 예약값 0, 종류 1에서는 폴리곤 성분 번호 |

타일 번호와 페이지 번호를 요청한 레코드와 대조한다. `MIXED` 타일의 페이지 순서는 하나 이상의 패리티 페이지 뒤에 하나 이상의 링 체인 페이지가 오는 순서다. 링 체인이 시작된 후 패리티 페이지가 다시 나오면 오류다.

### 5.1 종류 0: 원거리 교차 패리티

오프셋 32부터 f64 위도 이벤트 `count`개가 이어진다. 총 길이는 `32 + 8*count`다. 시작 패리티는 0 또는 1이며, 해당 타일의 첫 패리티 페이지 이외에는 0이다. 이벤트는 유한한 값으로 엄격히 증가하고 `tile_south < event <= tile_north`를 만족한다. 여러 패리티 페이지로 나뉘어도 전체 이벤트 순서는 엄격히 증가한다.

각 페이지가 질의 위도 `y`에 기여하는 패리티는 다음과 같다.

```text
base XOR (event <= y인 이벤트 개수의 홀짝)
```

이벤트가 하나도 없는 패리티 페이지도 유효하다. 원거리 교차가 없음을 나타내는 경우에도 `MIXED` 타일의 패리티 시작 페이지는 남긴다.

### 5.2 종류 1: 원본 링 체인

| 오프셋 | 바이트 수 | 내용 |
| ---: | ---: | --- |
| 32 | 4 | 원본 링 안에서 첫 선분의 번호 |
| 36 | 4 | 외곽선 0, 구멍 1 |
| 40 | `16*(count+1)` | 원본 `(longitude, latitude)` 정점 `count+1`개를 바이트 레인별로 재배열한 자료 |

총 길이는 `40 + 16*(count+1)`이다. 선분 `count`개에는 정점 `count+1`개가 필요하다. 체인은 링 전체가 아닌 연속 선분 일부일 수 있으므로 체인마다 닫힘을 요구하지 않는다. 원본 링 전체를 복원했을 때 닫힘과 모든 원본 위치의 존재를 검사한다.

바이트 재배열은 좌표 값을 변경하지 않는다. `m = 2*(count+1)`이라 하고, f64 워드 순서를 `lon0, lat0, lon1, lat1, ...`로 잡는다. 워드 `w`의 little-endian 바이트 `lane`은 원시 페이지의 다음 위치에 저장된다.

```text
저장 위치 = 40 + lane*m + w
복원 위치 = 40 + 8*w + lane
0 <= lane < 8, 0 <= w < m
```

복원한 각 좌표는 유한하며 루트의 마스크 바운딩 박스 안에 있어야 한다. 링 번호와 폴리곤 번호는 헤더 개수 안에 있어야 하고, 구멍 표시는 0 또는 1이다. 같은 타일의 체인은 링 번호가 증가하는 순서이며, 같은 링 안에서는 원본 선분 구간이 겹치지 않는 순서다. 같은 링을 이어가는 체인은 폴리곤 번호와 구멍 표시가 일치해야 한다.

런타임의 `first + count < source_vertex_count` 검사는 전체 자료를 기준으로 한 구조적 범위 검사다. 각 링의 모든 위치가 정확하게 존재하는지, 타일 사이의 중복 복사본이 동일한지에 대한 검증은 [독립 재구성 검증기](../tools/verify_korea_boundary.py)가 원본 링과 대조한다. 루트 해시를 고정한 런타임 검증과 원본 기하를 대조하는 생성 단계 검증은 역할이 다르다.

## 6. 범위와 무결성 검사

런타임 판정기가 검사하는 주요 형식 한도는 다음과 같다. 현재 생성기의 조각 배치는 앞 절을 따른다.

| 항목 | 한도·조건 |
| --- | --- |
| 루트 파일 | 최대 8,388,608바이트 |
| 타일 | 1∼262,144개 |
| 조각 | 1∼4,096개 |
| 전체 페이지 | 1∼1,000,000개 |
| 조각 파일 | 최대 524,288바이트 |
| 해제 페이지 | 32∼32,768바이트이며 종류별 길이 식과 일치 |
| 체인 페이지 선분 | 1∼1,024개 |
| 패리티 페이지 이벤트 | 0∼4,092개 |
| 원본 정점 | 최대 20,000,000개 |
| `scale` | 1, 2, 4, 8, 16, 32, 64, 128, 256 |
| 격자 행·열 | 양수, Rust 파서에서는 각각 최대 4,096 |
| 마스크 경도 | `124 <= west < east <= 132` |
| 마스크 위도 | `32 <= south < north <= 40` |

루트의 타일 수는 행 수와 열 수의 곱이다. 격자 원점과 크기는 다음 식으로 실제 마스크 범위를 바깥에서 감싼다.

```text
grid_west  = floor(west*scale)/scale
grid_south = floor(south*scale)/scale
columns    = ceil(east*scale) - floor(west*scale)
rows       = ceil(north*scale) - floor(south*scale)
```

무결성 검증은 다음 연결을 따른다.

1. 코드에 고정한 SHA-256으로 `index.bin` 전체를 검사한다.
2. 루트에 저장된 SHA-256으로 필요한 조각 전체를 검사한다.
3. 조각의 원본 SHP 식별자, 시작 페이지, 개수, 길이를 루트와 대조한다. 웹은 원본 SHP 식별자도 별도 상수와 대조하고, Rust는 고정된 루트의 식별자를 조각과 대조한다.
4. 해당 페이지의 압축 스트림, 압축 체크섬, 해제 길이, 매직, 번호, 좌표 범위 및 메타데이터 순서를 검사한다.

잘못된 자료를 `OUTSIDE`로 바꾸지 않는다. `MIXED` 타일에서는 한 선분에서 경계 접촉을 발견했더라도 필요한 모든 페이지의 검증을 마친 뒤 결과를 반환한다. 필요한 페이지의 손상을 뒤늦게 발견했을 때도 오류가 전파된다. `INSIDE`·`OUTSIDE`는 루트 인덱스로 판정하므로 사용하지 않는 다른 타일의 지오메트리까지 매번 해제하지 않는다. [Rust](../src/korea_boundary.rs), [웹](../korea_boundary.js)

## 7. 타일 판정과 원본 `covers`의 동치

### 7.1 타일 소유권

도당 셀 수가 2의 거듭제곱이므로 타일 선의 좌표는 이진 부동소수점으로 정확하게 표현되는 격자에 놓인다. 내부 타일의 소유 범위는 `[west,east) × [south,north)`다. 내부 세로 경계의 점은 동쪽 셀, 내부 가로 경계의 점은 북쪽 셀이 소유한다. 전체 범위의 최댓값은 마지막 해당 셀로 보낸다. 이는 경계 위의 직접 `covers` 질의도 처리하기 위한 규칙이다.

Rust는 정렬된 격자선에서 `edge <= coordinate`인 위치를 찾고, 웹은 원점 차이에 `scale`을 곱해 내림한다. 둘 다 마지막 행·열을 넘지 않게 선택한다. 실제 후보 생성은 마스크 바운딩 박스 안에서 32비트 축 분율의 셀 중심을 변환하므로 바깥쪽 타일 격자 패딩에 후보를 추가하지 않는다.

### 7.2 세 가지 타일 상태

원본 선분의 닫힌 바운딩 박스가 타일의 닫힌 사각형에 닿으면 그 타일은 보수적으로 `MIXED`가 된다. 실제 선분이 사각형을 지나지 않아도 바운딩 박스가 닿으면 `MIXED`일 수 있다. 이는 계산량에 영향을 주지만 포함 영역을 바꾸지 않는다.

그러한 선분이 없는 타일은 독립 GEOS `covers(cell)`일 때만 `INSIDE`, `disjoint(cell)`일 때만 `OUTSIDE`로 저장한다. 타일 안의 작은 구멍이나 분리 성분에도 원본 경계가 있으므로 경계가 있는 셀을 이 빠른 경로로 생략하지 않는다. 타일 선과 정확히 겹친 경계도 양쪽 셀에서 `MIXED`로 남는다. [생성기의 타일 분류](../tools/build_korea_boundary.py)

### 7.3 로컬 선분과 원거리 패리티

질의점에서 동쪽으로 뻗는 수평 광선을 생각한다. 원본 선분을 다음과 같이 나눈다.

- 닫힌 바운딩 박스가 타일과 만나는 선분은 원본 좌표 그대로 로컬 체인에 저장한다.
- 타일 동쪽 끝보다 `min(longitude)`가 큰 선분은 전부 타일 오른쪽에 있다. 이 선분의 광선 교차 여부는 질의점의 경도가 아니라 위도 구간 `[min_y,max_y)`만으로 결정된다.
- 타일 왼쪽에만 있는 선분이나 타일 행과 위도 범위가 겹치지 않는 선분은 해당 질의의 오른쪽 광선에 기여하지 않는다.

원거리 선분에 대해 `tile_south`를 포함하는 반열림 위도 구간의 개수로 시작 패리티를 정한다. 이어서 `tile_south < y <= tile_north`에 있는 구간 끝점을 모으고, 같은 f64 위도값이 짝수 번 나오면 서로 상쇄한다. 홀수 번 나오는 끝점만 이벤트로 저장한다. 따라서 저장된 시작 패리티와 이벤트 개수의 홀짝은 원거리 선분을 모두 직접 순회한 광선 교차 패리티와 같다.

로컬 선분은 `(start_y > y) != (end_y > y)`일 때만 교차 후보가 된다. 방향 행렬식의 부호가 상승 선분에서는 양수, 하강 선분에서는 음수일 때 동쪽 교차다. 이 반열림 규칙은 꼭짓점의 이중 계수를 막으며, 원거리 패리티의 `[min_y,max_y)`와 같은 규약이다.

전체 결과는 로컬 교차와 원거리 교차의 XOR다. 유효한 다중 폴리곤의 모든 외곽·구멍 링을 함께 판정하므로 구멍 내부는 제외되고 분리 성분은 포함된다. 방향 행렬식이 정확히 0이고 점이 선분의 닫힌 바운딩 박스 안에 있으면 별도로 경계 접촉을 기록한다. 마지막 결과는 `boundary_hit OR parity`이므로 외곽 경계와 구멍 경계는 포함된다.

질의점이 원본 경계에 있다면 그 선분의 바운딩 박스는 질의점을 소유한 타일과 반드시 만난다. 따라서 경계 접촉 검사는 로컬 체인만으로 충분하다. 이 분해에는 새로운 정점이나 타일 절단선이 필요하지 않다.

### 7.4 강건한 방향 판정과 재구성 검증

방향 판정은 먼저 두 곱의 차를 계산한다. 차의 절댓값이 `3.3306690738754716e-16 * (abs(left)+abs(right))`보다 클 때는 그 부호를 사용한다. 그렇지 않으면 분할 상수 `134217729`를 이용해 각 곱의 반올림 오차를 구하고, 네 항의 확장 합으로 부호와 정확한 0을 판정한다. 마스크의 좁은 경도·위도 범위에서는 좌표 차가 Sterbenz 조건을 만족하므로 입력 뺄셈의 오차 항이 추가로 필요하지 않다. 경계 주변을 잘라내거나 붙이는 epsilon은 사용하지 않는다. [공통 수치 연산](../src/geo_uniform.rs)

[재구성 검증기](../tools/verify_korea_boundary.py)는 체인을 폴리곤·링·구멍 표시·원본 선분 번호로 합친다. 타일 사이에 반복 저장된 정점 비트가 같은지, 링의 모든 위치가 존재하는지, 닫힘이 보존됐는지를 확인한다. 이어서 원본과 복원본의 모든 성분을 일대일로 대응시켜 무허용오차 좌표 동치, GEOS 동치와 빈 대칭차를 확인한다. 런타임의 해시 검증만으로 이 기하학적 동치를 주장하지 않는다.

## 8. GRS80 후보 좌표의 결정적 수치 규약

### 8.1 수학적 기준

위도 `phi`와 경도 `lambda`를 라디안으로 쓰면 목표 면적 요소는 다음에 비례한다.

\[
dA=a^2(1-e^2)\frac{\cos\phi}{(1-e^2\sin^2\phi)^2}\,d\phi\,d\lambda,
\qquad e^2=0.006694380022900787.
\]

폐형식 누적 함수는 다음과 같다.

\[
Q(\phi)=\frac{\sin\phi}{2(1-e^2\sin^2\phi)}
+\frac{\operatorname{atanh}(e\sin\phi)}{2e}.
\]

`lambda`와 `Q(phi)`에서 등간격인 셀이 수학적 기준의 등면적 셀이다. 후보를 원본 위경도 폴리곤에서 판정하며, 마스크의 선분을 이 공간의 새로운 직선으로 다시 해석하지 않는다.

### 8.2 Rust와 JavaScript가 공유하는 Q 근사 연산

제품은 플랫폼별 `sin`·`atanh` 함수 호출에 의존하지 않고 아래와 같은 binary64 다항식 연산을 공유한다. 입력 `latitude`는 도 단위이며 적용 위도 구간은 32∼40°다. 상수의 십진 표기는 아래 그대로 binary64로 변환한다. [Rust 수치 구현](../src/geo_uniform.rs), [동일한 웹 연산](../korea_boundary.js)

```text
DEGREES = 0.017453292519943295
e2 = 0.006694380022900787
d = (latitude - 36) * DEGREES
t = d * d
```

`H(t;c0,...,cn)`는 `p=cn`에서 시작해 `i=n-1,...,0` 순서로 `p=ci+t*p`를 적용하는 Horner 계산이다. 다음 계수를 사용한다.

| 차수 i | 사인 보정 계수 `si` | 코사인 보정 계수 `ci` |
| ---: | ---: | ---: |
| 0 | 1 | 1 |
| 1 | -0.16666666666666666 | -0.5 |
| 2 | 0.008333333333333333 | 0.041666666666666664 |
| 3 | -0.0001984126984126984 | -0.001388888888888889 |
| 4 | 2.7557319223985893e-6 | 2.48015873015873e-5 |
| 5 | -2.505210838544172e-8 | -2.755731922398589e-7 |
| 6 | 사용하지 않음 | 2.08767569878681e-9 |

이후의 순서는 다음과 같다.

```text
sine_delta = d * H(t;s0,...,s5)
cosine_delta = H(t;c0,...,c6)
s = 0.5877852522924731 * cosine_delta + 0.8090169943749475 * sine_delta
z = (e2 * s) * s
p = 9 / 17
계수 c를 [8/15, 7/13, 6/11, 5/9, 4/7, 3/5, 2/3, 1] 순서로 적용:
    p = c + z * p
Q_tilde(latitude) = s * p
```

분수는 binary64 나눗셈이다. 곱셈·덧셈·뺄셈·나눗셈을 표시된 결합 순서대로 각각 반올림하며, 곱셈과 덧셈을 FMA의 한 번 반올림으로 합치거나 산술을 재결합하지 않는다. 특히 `z`는 `e2*(s*s)`로 바꾸지 않는다. 이것은 두 언어의 비트 재현성을 위한 계산 규약이며, 폐형식 Q와의 수학적 오차가 0이라는 뜻은 아니다.

### 8.3 32+32비트 분할과 52회 이분법

입력은 `0 <= value <= 2^64-1`인 전체 정수다. Rust는 `u64`, JavaScript는 `BigInt`를 사용한다. 전체 `u64`를 먼저 부동소수점으로 바꾸지 않는다.

1. `uy = value >> 32`, `ux = value & 0xffffffff`로 나눈다.
2. 정확히 표현 가능한 32비트 정수에서 `fy=(uy+0.5)/4294967296`, `fx=(ux+0.5)/4294967296`을 계산한다.
3. `qs=Q_tilde(south)`, `target=qs+fy*(Q_tilde(north)-qs)`를 이 순서로 계산한다.
4. `lower=south`, `upper=north`로 시작한다.
5. 정확히 52회 반복한다. `middle=lower+(upper-lower)*0.5`를 계산하고, `Q_tilde(middle) < target`이면 `lower=middle`, 그 밖에는 `upper=middle`로 둔다. 같은 값일 때도 `upper`를 바꾼다. 허용오차에 따른 조기 종료는 없다.
6. `latitude=lower+(upper-lower)*0.5`, 이어서 `longitude=west+fx*(east-west)`를 계산한다.
7. 결과가 유한하고 두 축 모두 마스크 바운딩 박스의 엄격한 내부인지 확인한다. 범위를 벗어난 역산 결과는 오류다.

Rust의 반환 필드는 `Coordinates { latitude, longitude }`, 웹의 반환 배열은 `[latitude, longitude]`다. 경계 파일의 정점 저장 순서인 `(longitude, latitude)`와 구분한다.

### 8.4 수학적 오차와 언어 간 재현성의 별도 검증

두 언어가 같은 f64 비트를 반환한다는 검사만으로 Q 근사가 정확하다고 결론내리지 않는다. 검증은 다음을 분리한다.

- 고정밀 폐형식 Q 및 그 도함수와 대조해 근사·역산 오차, 단조성, 축 극단값과 셀 중심을 확인한다. 좌표 오차 검증에는 1e-12° 한도를 사용한다.
- 같은 입력·바운딩 박스에서 Rust와 JavaScript의 좌표 비트를 대조한다.
- 실제 출력에 대해 독립 원본 GEOS `covers`와 보조 난수 소비 순서를 확인한다.

고정밀 기준과 일치하는지, 서로 같은 계산을 수행하는지, 원본 마스크 안에 드는지는 서로 다른 검사다. Q의 부동소수점 근사와 유한 격자라는 한계를 연속 면적의 완전한 균등성으로 바꾸어 표현하지 않는다. [수치 단위 검증](../src/geo_uniform/tests.rs), [경계·보조 난수 검증](../src/korea_boundary/tests.rs)

## 9. 전체 64비트 거부 샘플링과 `supp`

첫 후보는 변경하지 않은 원본 `num_64`다. 첫 후보가 `covers`를 만족하면 보조 난수를 읽지 않는다. 거부할 때마다 공급자에게서 새로운 전체 64비트 값을 한 개 받아 두 축을 함께 다시 계산한다.

```text
proposed = num_64
supplemental_reads = 0
반복:
    point = candidate(proposed, mask.bounds)
    covers(point)이면 point 반환
    supplemental_reads == 1024이면 오류
    proposed = 공급자에게 요청한 새로운 전체 u64
    supplemental_reads += 1
```

다른 필드가 보조 난수를 소비한 뒤 다음 공급 순번을 사용한다. `RandomBitBuffer`에 남아 있는 비트나 이미 사용한 word를 대한민국 좌표의 새 후보로 재활용하지 않는다. 독립한 새 공급값이 우연히 이전과 같을 수는 있으며, 같은 정숫값을 금지하는 중복 제거 규칙은 없다. [호출자 연결](../src/random_data.rs)

보조 난수는 최대 1,024개다. 따라서 초기 후보를 포함해 최대 1,025개 후보를 검사한다. 마지막 허용 보조 후보의 수락은 가능하며, 그 후보도 밖이면 다음 공급자를 호출하지 않고 실패한다. 웹 generator는 새 보조 입력의 `bitsRemaining === 64`, `BigInt` 자료형 및 u64 범위를 확인한다. 공급자 오류, 취소 또는 경계 자료 오류는 재추출로 숨기지 않고 호출자에게 전파한다. 오류가 난 후보를 억지로 국토 안으로 옮기지 않는다. [Rust 샘플러](../src/korea_boundary.rs), [웹 generator](../korea_boundary.js)

## 10. 유한 격자의 조건부 균등성

각 축의 32비트 인덱스는 `2^32 × 2^32` 셀 중심을 지정한다. `C=2^64`, 수락되는 후보의 수를 `M>0`, 거부되는 후보의 수를 `R=C-M`이라 하자. 아래 확률식은 경계 자료와 공급자가 정상 동작할 때 적용한다. 초기값과 이후의 모든 보조 word가 서로 독립이고 전체 u64에서 균등하며, 같은 경계 버전에 대해 판정이 결정적이라는 조건을 둔다.

어떤 유효 후보 `j`가 `k`번의 거부 뒤 처음 수락될 확률은 모든 `j`에 대해 같다.

\[
P(\text{출력 }j,\;k\text{회 거부})=\frac{R^k}{C^{k+1}}.
\]

보조 읽기 한도가 `L`이면 다음과 같다.

\[
P(\text{출력 }j\text{와 성공})=
\frac{1-(R/C)^{L+1}}{M},\qquad
P(\text{출력 }j\mid\text{성공})=\frac1M.
\]

한도 실패 확률은 `(R/C)^(L+1)`이며 현재 `L=1024`다. 한도 실패를 임의 수락으로 바꾸지 않으므로 성공한 결과의 조건부 동일 가중치는 유지된다. 임의의 수동 `supp` 목록에는 독립 균등 입력이라는 전제가 없으므로 같은 통계적 보장을 주장하지 않는다.

이 식은 유한한 수락 집합의 동일 가중치에 관한 식이다. 연속 영역은 무한한 실수 점을 갖고, 경계를 가로지르는 셀은 중심점으로 포함 여부가 결정된다. 실제 마스크의 연속 면적을 곱해 `M`의 정확한 값을 얻었다고 주장하지 않는다. 근사 면적을 사용하는 통계 검사와 모든 유효 후보의 동일 가중치 증명도 구분한다.

[축소 격자 검증 도구](../tools/verify_reduced_lattice.py)는 구멍과 분리 성분을 가진 고정 합성 마스크에서 8+8비트 축의 65,536개 및 16+16비트 축의 4,294,967,296개 후보를 독립 정수 프로그램으로 전수 열거한다. 전체 word가 8비트인 더 작은 모델에서는 두 word의 65,536개 경로도 전수 열거한다. 이는 실제 대한민국의 `2^64` 후보를 전수 열거했다는 주장이 아니다.

## 11. 캐시, 선행 로딩과 메모리 회계

캐시와 선행 로딩은 같은 경계 자료를 다시 읽고 해제하는 비용을 줄인다. 후보, 결과 및 공급 순번에는 관여하지 않는다. 웹의 `prepareKorea`는 현재 원본 입력 후보에 필요한 자료를 미리 읽을 수 있지만 보조 난수를 요청하지 않는다.

| 대상 | 항목 수 제한 | 바이트 회계 제한 | 추가 동시성 제한 |
| --- | ---: | ---: | --- |
| Rust 작업자별 해제 페이지 | 4,096 | 1,048,576바이트 | 작업자별 가변 캐시 |
| 웹 압축 조각 | 8 | 4,194,304바이트 | 진행 중 최대 8개, 건당 524,288바이트 예약 |
| 웹 해제 페이지 | 4,096 | 4,194,304바이트 | 진행 중 최대 256개, 건당 32,768바이트 예약 |

Rust의 바이트 회계에는 페이지 payload와 살아 있는 deque 항목 크기가 들어간다. 웹은 진행 중 요청에 예약분을 먼저 부과하고, 완료되면 실제 보관 바이트로 바꾼다. 실패한 웹 캐시 항목은 제거하여 이후 호출에서 다시 시도할 수 있게 한다. 루트와 조각의 버전·해시 검사는 캐시 사용 여부와 관계없이 동일 자료를 가리키게 한다. [Rust 캐시](../src/korea_boundary.rs), [웹 캐시](../korea_boundary.js)

Rust 압축 해제기는 허프먼 트리마다 512개의 `u16`, 즉 1,024바이트의 9비트 조회표를 사용한다. 조회표로 처리할 수 없는 코드와 비트가 부족한 끝부분은 기존 비트 단위 판정으로 처리하며, 고정 허프먼 트리 한 쌍은 `LazyLock`으로 재사용한다. SHA-256은 블록별 64개의 `u32` 스케줄을 계산한 뒤 round 상수와 순서대로 결합한다. 이 작업 배열은 256바이트로, 이전 16-word 회전 배열보다 192바이트 크다. SHA를 지원하는 x86_64에서는 같은 스케줄에 전용 두 라운드 명령을 적용하고, 기능 감지가 실패하거나 다른 아키텍처이면 기존 scalar 라운드를 실행한다. SHA 변경은 새 heap 할당이나 경계 캐시를 추가하지 않는다. 배열 크기는 컴파일된 전체 stack frame이나 RSS의 차이를 뜻하지 않는다. [압축 해제 구현](../src/boundary_inflate.rs), [해시 구현](../src/korea_boundary/hash.rs)

웹 압축 해제기는 기존 9비트 조회표를 유지하고, 조회에 필요한 9비트를 두 바이트의 결합·시프트·마스크 연산으로 읽는다. 9비트 이상이 남았는지 먼저 확인하며, 긴 코드와 끝부분의 기존 처리 경로는 유지한다. 이 변경은 조회표나 캐시를 추가하지 않고 입력 비트의 읽기 방법만 바꾼다. [웹 압축 해제 구현](../korea_boundary.js)

**이 표는 전체 RSS나 JavaScript heap의 상한이 아니다.** 컨테이너의 남는 capacity, 객체·allocator 오버헤드, Promise와 진행 중 연산의 참조, 다운로드 조각을 합치는 임시 배열, 압축 해제 및 좌표 재배열 버퍼, 허프먼 표와 해시 작업 배열, 전역 인덱스와 Rust 실행 파일에 매핑된 내장 데이터는 따로 존재한다. Rust의 페이지 해제에는 32 KiB 작업 버퍼도 사용한다. 캐시 회계상 제한과 실제 프로세스·브라우저 메모리 실측을 구분해 보고해야 한다.
