# 대한민국 좌표 v2 균등성·초기 지연 검증

기준은 `7861a5379d71d0e2bddfb9d14c0c9281653d22bf`이며, 승인된 새 균등 버전으로 전환했다. 기존 v1 좌표 매핑은 바뀐다. v2의 동일한 기본 난수와 독립 보완 난수 순서는 Rust·JavaScript 및 사전 로딩·캐시 설정에 관계없이 같은 좌표와 난수 소비량을 낸다. 여러 레코드에 하나의 보완 목록을 공유하면 추가 소비로 뒤 레코드의 다른 필드도 달라질 수 있다.

채택한 SGIS·KEI 보정 경계의 모든 정점과 삼각형 연결 정보를 그대로 보존했다. 새로운 측량 자료로 작전 경계를 인증하거나 미확정 해안 영역을 추가한 작업은 아니다. 기존 하천·호수 포함 정책도 유지했다.

삼각형 수 5,165,448개, 페이지 20,178개, 폴리곤 성분 13,701개를 유지했다. 기하 페이로드 SHA-256은 전후 모두 `8a1fad5b174216f5a7f3142fd95e30622b5b986fade7cdbc6fa29c93b9b51566`이다. 최종 생성기로 원본 보정 SHP를 다시 빌드해 191개 바이너리 파일이 모두 바이트 단위로 일치함을 확인했다. v1 경계 파일은 v2로 교체했다.

균등성은 삼각형 제안 가중치와 수락 확률을 함께 보정한다. 위도 φ의 GRS80 면적 밀도를 `J(φ) = cos(φ)/(1-e²sin²(φ))²`로 두고, 평면 삼각형 면적 A와 남단 위도의 밀도 상한으로 정수 가중치 w를 만든다. 정수 선택의 상위 잔여 구간을 재추출하고, 독립 난수 두 개로 삼각형 내부 후보를 만든 뒤 `A × K × J(φ) × 10⁶ / w`로 수락한다. 제안 확률 `w/W`, 삼각형 내부 밀도 `1/A`, 수락 확률을 곱하면 위치별 밀도는 `J(φ)`에 비례한다. 정수 가중치 반올림도 이 수락식에서 상쇄된다.

안쪽 여유는 제거했다. 반올림된 후보가 실제 선택 삼각형 밖에 있을 때만 재추출한다. 이상적인 연속 수학 모형의 동일 지표면 면적 확률이 같으며, 구현에는 binary64 좌표·52비트 내부 난수의 유한 정밀도가 있다. 통계 검정 통과를 문자 그대로의 연속 분포 증명으로 해석하지 않는다.

검정 유의수준은 사전에 정한 10⁻⁶이다. 검사용 영역의 균등성은 실제 샘플러와 동일 코드를 작은 합성 경계에 연결해 검사했다. 실제 경계는 모든 파일 해시·압축·정수 누적합과 전체 삼각형 상한을 검사했다. 독도 동·서도, 마라도, 백령도, 대청도, 연평도, 고성 접경부 도달성도 별도 확인했다.

초기 지연은 Chrome Headless Shell 151.0.7922.34에서 실제 난수 생성·변환 UI를 사용해 9회씩 교차 측정했다. 새 페이지마다 모듈·응용 캐시를 비웠다. 네트워크 실험은 모듈·인덱스·조각 요청마다 40ms와 응답 본문 크기/20Mbps를 더하는 고정 모형이다. 브라우저 시작·HTML 탐색은 제외한다. 절대 시간을 일반 인터넷 환경의 보장값으로 해석하지 않는다.

| 실제 main v1 → 최종 v2 | 기존 중앙값 | 수정 중앙값 |
| --- | ---: | ---: |
| 루프백, 생성 즉시 변환 클릭 | 38.4ms | 22.7ms |
| 고정 네트워크, 생성 즉시 변환 클릭 | 559.0ms | 355.7ms |
| 고정 네트워크, 생성 200ms 뒤 클릭 후 대기 | 559.6ms | 153.2ms |
| 루프백, 생성 200ms 뒤 클릭 후 대기 | 34.7ms | 3.2ms |
| 첫 좌표에 필요한 응답 본문 합 | 1,014,296 bytes | 536,561 bytes |

200ms 사전 로딩 시간은 숨긴 작업 시간이 아니다. 고정 네트워크의 생성 시작부터 완료까지는 기존 약 760ms, 수정 약 354ms였다. 모듈 URL에도 v2 식별자를 붙여 새 HTML과 이전 JavaScript 캐시가 섞이지 않게 했다. 최종 URL에서 위 성능값을 다시 측정했고, 이전 모듈 응답을 의도적으로 실패시키는 브라우저 검사도 통과했다. 사전 로딩 자체는 난수를 소비하지 않는다. v1과 비교할 때 승인된 국내 좌표 차이를 제외한 첫 레코드의 다른 필드는 일치했다.

동일한 v2 알고리즘·기하·난수열을 사용하는 후보끼리도 비교했다. 고정 네트워크에서 생성 200ms 뒤 클릭한 경우, 평면 인덱스 지연 로딩 564.8ms, 계층 인덱스만 360.9ms, 루트 사전 로딩 266.4ms, 대상 페이지 사전 로딩 157.8ms였다. 각 9회의 중앙값이다. 최종 두 후보의 기존 v1과의 별도 교차 측정값은 위 표와 같으며, 실험군별 변동을 합쳐 하나의 숫자로 만들지 않았다.

반복 변환은 서로 다른 기본 난수 10,000개와 독립 보완 난수 시드로 구성한 같은 입력군을 한 번 준비한 뒤 다시 변환했다. 각 후보 9회 교차 측정했다. 모든 출력 좌표의 비트와 난수 소비량을 Rust 기준값과 비교했다.

| v2 후보 | 10,000개 재변환 중앙값 | 범위 |
| --- | ---: | ---: |
| 평면 인덱스·128페이지 | 650.2ms | 558.7–792.8ms |
| 계층 인덱스·128페이지, 조각 인덱스 별도 보존 없음 | 736.7ms | 594.8–877.3ms |
| 조각 인덱스 별도 보존·128페이지 | 660.1ms | 590.8–1,056.6ms |
| 조각 인덱스 별도 보존·256페이지, 적용 | 49.3ms | 46.8–53.6ms |
| 조각 인덱스 별도 보존·512페이지 | 53.2ms | 45.2–63.5ms |

이 입력군은 서로 다른 좌표 10,000개가 245개 페이지를 공유했다. 128페이지에서는 재변환 때도 338회 압축 해제가 발생했고, 256·512페이지에서는 0회였다. 조각 인덱스를 따로 보존하면 해제 페이지가 남아 있을 때 압축 조각을 다시 내려받지 않는다. 512페이지의 추가 이점은 관측되지 않아 256페이지를 선택했다. 모든 입력군에 같은 배율을 보장하는 결과는 아니다.

메모리 증가는 명시적인 절충이다. 웹은 압축 조각 8개, 해제 페이지 256개, 전체 조각 인덱스 325,888 bytes로 제한한다. 루트까지 합친 원시 보존 버퍼의 상한은 약 8.2MiB이며 객체·엔진 오버헤드와 진행 중 응답은 별도다. 10,000점 뒤 GC를 수행한 3회 관측에서 평면 v2의 V8 backing storage 중앙값은 6,133,556 bytes, 최종은 6,958,629 bytes였다. JS heap은 약 1.80MB에서 1.83MB였다.

Rust 작업자 캐시는 기존 32페이지·순수 버퍼 약 496KiB를 유지하며, 작업자 종료·중단 시 해제된다. Linux `/proc` VmHWM을 약 1ms 간격으로 관측한 1만 건 생성 9회의 중앙값은 기존 18,256KiB, 수정 20,324KiB였다. 파일 배치·실제 난수·스레드 실행에 영향을 받는 근사 관측치다. Python fork의 메모리 이력이 섞인 최초 wait4 RSS 수치는 폐기하고 시간 결과만 보존했다.

Linux release의 실제 `generate 1`·`generate 10000`도 하드웨어 난수와 파일 쓰기를 포함해 각각 9회 비교했다. 1건 중앙값은 7.04→6.89ms, 1만 건은 106.7→108.3ms였다. 1만 건의 범위는 기존 98.0–120.4ms, 수정 104.1–117.9ms로 겹친다. 이 전체 경로에 유의미한 속도 향상이 있다고 주장하지 않는다. 분리한 좌표 계산 10만 건은 32페이지 캐시 중앙값 2.025→1.899초, 캐시 없이 12.627→12.349초였다. 분리 계산에는 재현 가능한 보완 난수를 사용했다.

검증 도구는 Rust 1.99.1, LLVM 23.1.1, Playwright 1.62.1, Chromium 151.0.7922.34·Firefox 153.0·WebKit 26.5다. Cargo 런타임 의존성 0개, 기존 release 설정과 패키징 경로를 유지했으며 PGO를 사용하는 저장소가 아니다.

네이티브·브라우저 최종 필수 표면은 7/7 완료했다. Clippy의 경고 정책을 변경하거나 경고를 숨기지 않았다. Windows 임시 검증 도구에서 UTF-8 로그 디코딩과 stdout EOF 뒤 프로세스 종료 대기의 문제를 수정했다. 제품 코드는 이 재검증 과정에서 바뀌지 않았다. 첫 Windows 실패를 성공으로 계산하지 않고 마지막 실행의 완료 증거를 사용한다.

검증 실행은 [Linux·macOS·브라우저](https://github.com/krwizxp/srg/actions/runs/40702618145), [최종 모듈 URL·브라우저](https://github.com/krwizxp/srg/actions/runs/40706310960) 및 [Windows 최종](https://github.com/krwizxp/srg/actions/runs/40703620207)에서 확인할 수 있다. 해당 임시 워크플로와 계측 코드는 제품 커밋에서 제거했다. 영구 CI·지원 정책·Cargo 설정은 바꾸지 않았다.

M1 시간, M2 메모리, M3 배포 크기, M4 검증 완료율, M5 결과 일치, M6 균등 계약과 두 로딩 병목, M7 소스 변화, M8 회귀를 함께 평가했다. 런타임 원본 범위의 물리 LOC는 14,202→14,361이며, 생성 코드·테스트·문서를 제외한다. 자세한 코드 LOC와 모든 시간 표본은 [측정 데이터](uniform-performance-20261028.json)에 기록했다. 이 변경은 코드 축소를 근거로 채택한 것이 아니다. 승인된 v2 매핑·보완 소비 변경과 명시한 메모리 절충 외에 확인된 제품 회귀는 없다.
