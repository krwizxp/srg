# 대한민국 좌표 v4 추가 성능 개선과 Nu 예외

2026-10-29의 후속 요청인 “성능을 더 개선한 후 Nu 오류 9건은 예외로하세요.”에 따라 직전 v4를 별도 기준으로 고정하고 성능을 개선했다. 원래 Git 기준은 `c2da4b054e9045c96d0d335c7f8ea20b0edcaa63`이며, [첫 v4 구현 보고서](korea-v4-validation-20261029.md)의 측정값은 해당 체크포인트의 기록으로 보존한다.

이번 비교의 직접 기준은 기존 v4 ELF `e4898c989daf0437d7fc1fffad37bfa6208a9976036e6db3fa6823802f024e59`, JS `94f8206937d10cc03e992dd15b174ad20cf3707c979a8d482fe9e80bb9659785`, 데이터 루트 `8cb20a5c0da9c3d6225efb0323e24a4f992eb3029a772da3a71a55d3f503bf17`다. 원래 v3와 직전 v4를 혼용해 개선율을 계산하지 않는다. Rust는 같은 최적화 주기에 고정한 1.99.1을 사용했다.

## 1. 보호한 계약과 채택 기준

원본 위경도 폴리곤, 32+32비트의 GRS80 등면적 후보, 52회 결정적 이분법, 새 전체 supp64를 사용하는 거부 샘플링, 1,024개 보완 한도, 오류·취소·출력 원자성을 유지한다. 좌표의 binary64 비트와 순서가 있는 보완 입력의 소비량을 직전 v4와 정확히 비교한다. 수학 모듈은 변경하지 않았다.

기존 Rust 캐시는 payload와 살아 있는 항목의 회계상 합계가 작업자당 1 MiB이며, 웹 payload 예산은 압축 조각 4 MiB와 해제 페이지 4 MiB다. 이 상한과 외부 런타임 의존성 0개를 보호했다. 새 수신 API, WASM, 추가 서비스, 임의 지리 단순화는 도입하지 않았다. 객체 메타데이터·일시 작업 공간 등 회계 밖 비용이 있으므로, 예산과 별도로 프로세스 최대 RSS를 측정했다. 객체별 메타데이터를 따로 실측했다고 주장하지 않는다.

후보를 해석하기 전에 단발 탐색과 반복 확인을 구분했다. 최종 성능 확인은 같은 환경에서 기준·후보를 교차 실행하며, 단순 성능 변경에는 5% 이상, 추가 구조가 필요한 변경에는 10% 이상의 실행시간 감소를 목표로 정했다. 데이터 재배치의 크기 증가 한도는 1%였다. 잡음 범위의 후보를 계속 조정하거나 기준을 낮춰 채택하지 않는다.

## 2. 병목과 적용한 변경

### Rust 압축 해제

고정 10,000건의 진단 하네스에서 전체 약 1.540초 중 inflate가 0.955초, 최초 조각 SHA·인덱스 검증이 0.385초였다. 수학은 0.086초, 정점 복원은 0.054초, LRU 선형 검색은 0.0055초였다. 캐시 검색만을 이유로 새 해시 테이블이나 복잡한 캐시 정책을 만들지 않았다.

고정 Huffman 트리를 프로세스당 한 번 구성해 재사용하고, 9비트 이하의 짧은 코드를 512개 u16 조회표로 해석한다. 긴 코드와 입력 끝의 짧은 잔여 구간은 기존 decoder를 사용한다. 불완전 트리 거부, 정상 단일 심볼·빈 distance 예외, 출력 상한, Adler-32, trailing bytes 검증을 유지한다.

각 조회표는 1,024바이트이며 고정 트리 상태는 프로세스 수명 동안 유지된다. 동적 트리 작업 공간과 기존 32 KiB 해제 버퍼는 페이지 캐시 payload에 포함되지 않는다. 이 비용은 압축 해제 시간 감소와 함께 평가한다.

### Rust SHA-256

기존 구현은 매 round에 16개 word 배열을 회전했다. 표준 64-word schedule을 먼저 확장한 뒤 round 상수와 순서대로 읽도록 바꿨다. 반복 회전과 round 분기를 제거하며 알고리즘, 길이 검사, 패딩, 결과 바이트는 같다.

실제 기존 경계 파일 97개·50,276,630바이트의 독립 5회 비교에서 해시 시간 중앙값은 362.63 ms에서 206.29 ms로 43.11% 감소했다. 실제 파일 전부와 33개 기지·패딩 경계 벡터가 Python hashlib 기준과 일치했다. 작업 배열은 64바이트에서 256바이트로 192바이트 늘지만 heap·의존성·unsafe·아키텍처 전용 명령을 추가하지 않는다. 이 배열 차이를 전체 stack frame이나 RSS의 실측 증가량으로 표현하지 않는다.

### 채택하지 않은 JavaScript 짧은 코드 조회

기존 9비트 lookup의 일반 `peek(9)` 호출을 두 바이트를 읽는 고정 폭 연산으로 바꿨다. 기존의 입력 잔여 비트 검사, 긴 코드·끝 구간 fallback, 트리와 출력 검증은 유지한다. 두 바이트는 0–7비트 시프트 뒤 필요한 9비트를 모두 담는다. 수신 API와 캐시 구조는 바꾸지 않는다.

후보는 JS 코드 2줄 증가이며 SHA는 `befe878c22c1ec2307ff36ed4f48c3a1aba8f40bf0c5bc8750bdd114077bb71c`였다. 전체 25,348개 압축 페이지의 84,560,888바이트를 Python zlib와 비교하고 정상 10개·손상 1,506개 fixture의 이전 판정 일치도 확인했다.

하지만 원래 데이터 배치에서 최종 5회 교차 비교 결과, 10,000건 중앙값은 8.2612초에서 7.8773초로 4.647% 줄었다. 사전에 정한 5% 이상 기준에 못 미쳐 이 변경도 철회했다. 후보의 범위는 7.8526–8.0889초, 기준은 8.1494–8.6722초였으며, 작은 관측상 이득을 없었다고 표현하지는 않는다. 다만 결과를 본 뒤 채택 문턱을 낮추거나 표본을 계속 늘려 통과시키지 않았다. 최종 웹 소스는 직전 v4와 같다.

### 제외한 조각 재배치와 응답 지연 검증

직전 v4의 Chromium 고정 코퍼스에서는 23,876회 페이지 접근 중 22,714회가 해제 캐시 miss였으며, 압축 조각을 2,160회 다시 획득했다. 브라우저 HTTP 캐시로 실제 네트워크 요청이 줄어들어도 약 1.11 GB를 수신 경로와 SHA 검사에 다시 통과시켰다. 이 비용을 줄이려고 타일을 가능한 한 함께 넣는 64 KiB 조각과 4 MiB·64항목 압축 캐시를 시험했다.

이 후보는 원본부터 다시 생성한 916개 바이너리가 독립 재포장 결과와 전부 같았으며, 원본 정점·공간 판정도 보존했다. 하지만 **정확성 통과와 최종 성능 채택은 별개**다. 동일 입력의 localhost Chromium 5회에서 10,000건 중앙값이 8.2652초에서 4.9948초로 39.57% 줄었지만, 실제 HTTP 요청은 98회에서 733회로 늘었다. 이때 수신·해시 경로의 반복 바이트는 약 1.112 GB에서 127.8 MB로 줄었다. 작은 조각의 CPU·본문 처리 이득만으로 원격 환경의 결과를 판단하지 않았다.

추가로 실제 서버 요청의 응답을 20ms 늦추고 일반 HTTP 캐시는 유지하는 조건을 계획에 기록한 뒤 시험했다. 캐시 hit에는 서버 지연이 추가되지 않는다. 이 조건은 **통제한 합성 응답 지연**이며 실제 GitHub Pages 측정이나 모든 WAN 특성의 모사가 아니다. 각 후보 1회·고정 10,000건으로 큰 회귀를 판별하는 목적이다.

| Chromium 구성 | 10,000건 | 실제 HTTP 요청 | 실제 응답 본문 |
| --- | ---: | ---: | ---: |
| 직전 v4 | 10.7179초 | 98 | 50,310,422 B |
| 기존 조각 + quick9 | 10.0111초 | 98 | 50,310,545 B |
| 64 KiB 조각 + quick9 | 20.6620초 | 733 | 40,897,048 B |

64 KiB 후보는 기존보다 92.78% 느려져 제외했다. 기존 조각+quick9는 이 단발 조건에서 6.59% 빨랐지만, 별도의 5회 localhost 비교에서는 위의 5% 채택 기준을 만족하지 못해 함께 제외했다. 실제 서버 대기 범위는 19.16–23.61ms였고, 모든 좌표 비트와 보완 소비량은 일치했다. 요청별 경로·본문 크기·실제 대기와 raw 결과를 보존한다.

64 KiB 후보의 WebKit localhost 5개 완료 표본에서도 대량 시간은 줄었지만 첫 변환 중앙값은 32ms에서 171ms로 늘었다. 도중 브라우저 대상 종료 1회는 성공으로 세지 않았고, 원인이 확인되지 않은 채 새 process의 마지막 1쌍으로 나머지 표본을 확보했다. 이 후보의 중단과 초기 지연도 기록에 남긴다. 최종 성능 표에는 폐기한 64 KiB의 수치를 사용하지 않는다.

128 KiB 후보는 단발 탐색만 했고, 32 KiB는 접근 추적 모형만 평가했다. 중간 크기를 계속 탐색하거나 새 네트워크 계층을 추가하지 않고 원래 조각 배치를 유지하기로 했다. 수신 버퍼 선할당은 단발 1.18% 느려 제외했고, async wrapper 제거의 약 1.75% 차이는 채택 기준에 못 미쳤다. 공통 수학의 상수·탐색 변경도 전체 시간에 대한 충분한 개선 근거가 없어 적용하지 않았다.

## 3. 최종 데이터와 캐시

최종 데이터는 직전 v4의 97개 바이너리 및 manifest·원본 검증 파일과 전부 바이트가 같다. 생성기와 Rust embed도 직전 v4와 같다. 64 KiB 실험의 새 파일·manifest·embed·생성 정책을 실제 제품에서 모두 제거하고, 별도 호출에서 전체 파일 일치와 최종 해시를 다시 확인했다.

| 항목 | 직전 v4 | 최종 최적화 v4 |
| --- | ---: | ---: |
| 압축 조각 | 96 | 96 |
| 페이지 | 25,348 | 25,348 |
| 루트 인덱스 | 499,628 B | 499,628 B |
| 전체 경계 `.bin` | 50,276,630 B | 50,276,630 B |
| 조각 상한 | 524,288 B | 524,288 B |
| 실제 최대 조각 | 524,259 B | 524,259 B |
| 웹 압축 캐시 | 8개 / 4 MiB | 8개 / 4 MiB |
| 웹 해제 캐시 | 4,096개 / 4 MiB | 4,096개 / 4 MiB |

경계 데이터 증가는 0바이트다. 원래 v3의 103,444,465바이트 대비 51.40% 감소한 첫 v4의 결과를 유지한다. 13,701개 성분, 13,713개 링, 5,205,473개 원본 정점과 무손실 검증 근거도 그대로다.

최종 루트 SHA-256은 다음과 같다.

```text
8cb20a5c0da9c3d6225efb0323e24a4f992eb3029a772da3a71a55d3f503bf17
```

Rust와 JS의 핀은 이 값이다. 최종 JavaScript SHA는 `94f8206937d10cc03e992dd15b174ad20cf3707c979a8d482fe9e80bb9659785`이며, HTML도 기존 `?v=4`를 그대로 사용한다. 기존 압축 조각의 SHA가 붙은 URL과 바이너리 v4/004 형식은 같다. 진행 중 압축 조각 최대 8개와 512 KiB 예약, 해제 페이지 최대 256개와 32 KiB 예약도 유지한다. payload 예산은 전체 JS heap이나 브라우저 프로세스 RSS의 상한을 뜻하지 않는다.

## 4. 최종 실행시간·메모리·크기

### Linux 실제 release와 고정 코퍼스

직전 v4와 최종 v4를 각각 5회 교차 실행한 중앙값이다. CLOCK_MONOTONIC·fork/exec/wait4를 사용하는 C 래퍼로 wall time과 자식 최대 RSS를 측정했다. 고정 코퍼스는 단일 작업자 하네스이고 실제 CLI는 기존 병렬 배치 경로이므로, 두 경로의 절대 시간을 직접 비교하지 않는다.

| 항목 | 직전 v4 | 최종 v4 | 변화 |
| --- | ---: | ---: | ---: |
| 고정 입력 10,000건 | 1.329995초 | 0.751793초 | 43.47% 시간 감소 |
| 실제 CLI 10,000건 | 0.256388초 | 0.138026초 | 46.17% 시간 감소 |
| 고정 입력 10,000건 최대 RSS | 52,608 KiB | 52,672 KiB | 64 KiB·0.122% 증가 |
| 실제 CLI 10,000건 최대 RSS | 69,436 KiB | 69,636 KiB | 200 KiB·0.288% 증가 |
| 실제 CLI 1건 | 8.837 ms | 7.269 ms | 짧은 측정, 범위가 겹침 |
| 실제 CLI 1건 최대 RSS | 6,452 KiB | 6,580 KiB | 128 KiB 증가 |
| ELF | 50,944,864 B | 50,950,272 B | 5,408 B·0.0106% 증가 |
| 공식 비압축 TAR | 50,946,560 B | 50,952,192 B | 5,632 B·0.0111% 증가 |
| 같은 DEFLATE9 ZIP | 49,845,095 B | 49,846,081 B | 986 B·0.0020% 증가 |

고정 10,000건 시간 범위는 기존 1.281899–1.354202초, 최종 0.701039–0.767200초였다. 실제 CLI 10,000건은 기존 0.198108–0.275304초, 최종 0.119529–0.150933초였다. 모든 첫 회차를 포함했고 OS 파일 캐시를 비우지 않았으며, 같은 환경의 관측치로서 보고한다. 형식적인 통계적 유의성 검정을 주장하지 않는다.

실제 CLI는 HW RNG를 사용하므로 두 버전의 난수열이 다르다. 정확한 좌표·보완 입력 소비의 비교는 고정 코퍼스에서 별도로 수행했다. 단발 시간 범위는 기존 8.606–12.729ms, 최종 6.654–10.386ms로 겹쳐 단발의 확실한 개선율로 내세우지 않는다. 최대 RSS 중앙값은 약간 늘었고 범위도 겹친다. 메모리 감소를 주장하지 않으며, 실제 값과 캐시의 회계상 상한을 구분한다.

최종 고정 100,000건은 1회 5.446666초·최대 RSS 52,844 KiB였다. 이전 독립 원본 검증 출력과 좌표 binary64·보완 읽기 수가 전체 파일 바이트까지 일치했다. 출력 SHA-256은 `31c1a4b2ad83e9204bb4eb502ea3e06b578a1692d58b50449ca16c2ee01214be`다. 이 단일 대량 검사를 5회 성능 비교로 표현하지 않는다.

최종 ELF SHA-256은 `3d12310ba41743e7a667021beeec861004ff73fe3a64aa2e30935573f527b50e`다. 공식 TAR과 보조 ZIP의 내부 실행 파일도 동일하다. 공식 TAR SHA는 `9314561488682e30144952faf062ea8a061a995587799f703641c6872fda4c33`, 보조 ZIP SHA는 `f740a4196d32dc10400d87f8268cfcb46745320fd121608cc498079c8528f643`다. Cargo 프로필·lockfile·의존성을 바꾸지 않았으며 실제 PGO 사용은 없다.


### 브라우저 최종 구성

웹 성능 후보는 모두 철회했으므로 이번 최종판의 웹 개선율을 주장하지 않는다. JavaScript·HTML·전체 데이터가 직전 v4와 정확히 같음을 확인했고, 10,000건 원래 소스의 마지막 5개 측정 표본은 중앙값 8.2612초, 범위 8.1494–8.6722초였다. 최초 변환 중앙값은 27.0ms, 같은 점의 warm 변환은 0.1ms, 레코드별 p95는 4.7ms였다. 실제 요청 98회·50,310,422바이트에는 임시 계측 모듈이 포함된다.

이 측정은 새 브라우저 컨텍스트, localhost HTTP, 고정 num64/supp64 코퍼스와 일반 HTTP 캐시에서 수행했다. 최초 import·한 점의 cold/warm 변환을 먼저 측정하고 10,000건 loop를 따로 쟀다. 새로운 OS 부팅이나 콜드 디스크 상태가 아니며, 서버 지연 시험과 섞어 중앙값을 계산하지 않았다. 웹의 반복 수신·해시 비용과 기존 전체 heap 관측의 한계는 첫 v4 보고서에 남아 있다. 같은 캐시 한도라는 이유로 전체 브라우저 RSS가 제한된다고 주장하지 않는다.

## 5. 최종 정확성·오류·취소 검증

최종 Linux release build와 17개 release tests가 통과했다. 고정 10,000건의 5회 쌍 및 고정 100,000건에서 좌표 비트와 보완 소비량이 기존 v4와 일치했다. 실제 CLI 1건·10,000건의 20회 실행이 성공했으며 BOM·17개 완전한 출력 필드·기존 배치 경로를 확인했다.

실제 출력의 독립 GEOS `covers` 검사는 기준판 56,006개와 최종판 66,004개, 합계 122,010개에서 경계 밖 0건이었다. 최종의 정상 생성 50,005개 중 최초 후보가 밖이었던 37,778개는 모두 교체됐고, 안이었던 12,227개는 모두 독립 좌표 기준의 허용오차 1e-12도 이내에서 원래 후보와 일치했다. 이 실제 CLI 검사는 고정 코퍼스의 exact-bit 비교와 구분한다. 실제 CLI 내부의 보완 소비 개수는 외부에서 관찰하지 않으므로 그 수를 이 검사에서 추정하지 않았다.

수동 입력 성공 출력은 golden 파일과 바이트가 같았다. 보완 EOF와 공급자 EOF, 1,024회 거부 한도, 메뉴 EOF, Enter 중단 및 빈 디렉터리의 독립 실행을 두 버전에서 14개 CLI 계약 검사로 확인했다. 일반적인 비EOF 공급자 실패의 전파는 release 단위 테스트에서 확인했다. 정상 EOF 종료 정책과 오류의 종료 코드, 실패 시 부분 레코드를 남기지 않는 성질을 유지했다.

최종 웹 파일과 경계 바이너리 97개는 직전 검증판과 바이트가 같다. 이 동일성과 보고서 해시를 연결해 Node의 18개 계약 검사·10,650개 공간 점, 세 브라우저의 성분 도달성 13,711개씩, 고정 출력·TXT·실제 UI 10,000건·원본 GEOS 증거를 재사용했다. 이를 이번에 다시 전량 실행했다고 표현하지 않는다. TXT 근거는 localhost에서 제공한 HTML에서 로컬 TXT를 선택하고 경계 요청 없이 분석한 경우이며, `file://`로 HTML을 열었음을 뜻하지 않는다.

이전 UI의 일부 페이지에서 pageerror 감시 등록이 늦었던 관찰 범위는 새 검사로 보완했다. 최종 실제 HTML·JS·데이터에서 Chromium 151.0.7922.34, Firefox 153.0, WebKit 26.5 각각 수동 supp 성공, 수동 취소, crypto 실패, 실제 자동 supp 성공, 진행 중 geometry 요청에서 clear, 캐시된 거부 반복에서 clear의 6개 시나리오를 수행했다. 총 18개가 통과했고 모든 페이지에서 이동 전에 등록한 감시의 pageerror는 0건이었다. 오류·취소를 확정하는 경우에만 통제한 crypto 값을 사용했다.

Rust 압축 해제 소스의 SHA는 `3d5914e2265978f2085dc436739d85c6f8b069525fb0f15545fc52f0c8112dd5`로 전체 페이지·오류 비교를 수행한 소스와 같다. 최종 데이터의 압축 페이지는 해당 실험과 내용·순서가 동일하다. 따라서 25,348개 페이지·84,560,888개 출력 바이트의 독립 oracle 일치, 정상 10개·손상 1,499개의 이전 Rust 오류 판정 일치 증거를 정확한 소스/데이터 연결로 재사용한다. 이 재사용을 새로 전량 실행한 것으로 표현하지 않는다.

수학 소스, 원본 폴리곤 및 압축 페이지가 바뀌지 않았으므로 첫 구현의 독립 고정밀·축소 격자 증거는 해당 부분에 계속 유효하다. 같은 페이지라는 이유만으로 런타임 변경의 검증을 생략하지 않았다. 최종 압축 해제기, 새 파일 집합, 실제 CLI와 웹 호출 경로는 다시 검사한다.

## 6. Nu 오류 9건의 승인된 예외

사용자의 이번 요청은 기존 Nu CSS 오류 9건에 대한 명시적 예외 승인이다. 새 오류나 다른 검사까지 예외로 확장하지 않는다.

최종 HTML은 VS Code 1.144.0의 실제 내장 HTML 포맷터를 적용했다. 후보 철회 후 직전 HTML을 복원하고 포맷터를 다시 실행했으며, 최종 바이트는 직전 v4와 정확히 같다. 출력 템플릿과 의미 있는 줄바꿈도 같다. HTMLValidate 11.17.0은 종료 코드 0·진단 0이다. Nu 26.10.12는 종료 코드 1·오류 9·경고 0이며, 기존 아홉 메시지와 정확히 같다. 새 진단은 0건이다.

예외 목록은 `field-sizing` 1건, `anchor-name` 2건, `@position-try` 1건, `position-try-fallbacks` 1건, `position-anchor` 2건, `position-area` 2건이다. raw 검사 결과는 실패로 보존하고 인수 게이트 상태만 `accepted_user_exception`으로 표시한다. CSS 제거, 검사기 규칙 비활성화, 심각도 변경, 문서 제외 또는 영구 CI 변경은 하지 않았다.

최종 HTML SHA-256은 `625e7db05f6bd187f7f64342c81891b5925df6d4b67216015dbaf46fa9aeb0c2`다.

## 7. M1–M8과 남은 플랫폼 검증

고정된 도구 게이트 분모는 18개다. 네 타깃 Clippy 4개, 네이티브 build 4개, 네이티브 tests 4개, Rust format 1개, 브라우저 3개, HTML 검사기 2개로 나눈다. 응답 지연 시험은 M1·M8의 추가 인수 근거이며 이 분모에 더하지 않는다.

최종 네 타깃의 기존 정책 Clippy와 Rust format을 다시 실행했다. Clippy 종료 코드는 모두 0이며 bin 경고는 직전 106개에서 109개, tests는 211개에서 214개다. 새로운 SHA schedule의 인덱스는 16..64 반복 범위로 안전성이 정해져 있지만 기존 경고 수준에서는 indexing 경고가 남는다. 경고를 없애기 위한 `allow`·`expect`·심각도 변경은 없다. 일반 Clippy 통과를 경고 0이나 `-D warnings` 통과로 표현하지 않는다.

최종 결과는 **18개 중 통과 11개, 승인된 Nu 예외 1개, 미실행 6개**다. Nu raw 종료 코드 1은 그대로이며, 도구가 정상 종료한 12개로 세지 않는다. 미실행은 Windows MSVC, Intel macOS, Apple Silicon macOS의 네이티브 release build와 tests 각 2개다. 실행한 Linux·정적 검사·브라우저·HTMLValidate의 성공과 이 제약을 함께 보고하며 전체 플랫폼 인수가 완료됐다고 선언하지 않는다.

M5의 좌표·보완 소비 계약은 동일 입력으로 검사하고, 첫 v4에서 승인된 다른 필드의 보완 스트림 이동은 별도 역사적 증거로 유지한다. 이번 추가 성능 변경에 새로운 출력 규약 차이는 없다. M6에서 새로 확정한 기능 결함은 없으며, 64 KiB 요청 증가로 발생한 성능 회귀는 발견 후 철회했다.

M7의 동일 범위 코드 줄 수는 Rust runtime 1,528→1,585줄(+57), JS 703→703줄(변화 없음)이다. HTML 5,737줄, 테스트 476줄, 생성 Rust embed 103줄, 데이터 도구 643줄은 같다. 주석·공백 제외 방식과 파일 그룹은 첫 v4와 동일하며, 생성 코드나 도구를 runtime 절감량에 섞지 않는다. 코드 줄 수가 줄었다고 주장하지 않는다.

M8은 최종 실행한 검사에서 관찰한 기능 회귀, 실제 자원 변화, 미실행 플랫폼을 분리한다. 유지한 압축 해제 조회표와 SHA 작업 공간의 비용, 실제 RSS·배포 크기, 브라우저 지연·메모리의 측정 한계를 앞 절에 공개한다. 폐기 후보의 빠른 localhost 수치를 최종 이득으로 보고하지 않는다.

원래 프로젝트의 네 타깃을 유지한다. Windows MSVC·Intel macOS·Apple Silicon macOS의 교차 타깃 Clippy는 수행하지만, 해당 OS의 네이티브 링크·실행 증거로 대체하지 않는다. 별도 GitHub 반영·임시 workflow 승인 없이 원격 저장소에 기록하지 않았다. Nu 예외 승인을 다른 게이트의 면제로 취급하지 않는다.

## 8. 재현과 근거

정확한 소스·바이너리 해시, 반복 표본, 후보별 판정, 데이터 무손실 비교, Nu의 raw 진단과 예외 범위는 [통합 성능 검증 JSON](korea-v4-performance-20261029.json)에 기록한다. 원본 자료 확보와 전체 재생성 명령은 [README](../README.md), 파일 형식과 캐시 회계는 [v4 형식 문서](korea-v4-format.md)를 따른다.

## 9. GitHub 반영 전 검토할 구체적 범위

지시서 §8.6의 별도 승인 조건 때문에 현재 GitHub push·PR 작성·실제 CI 수정·워크플로 실행은 0회다. 검토용 전체 소스와 보고서를 먼저 완성하며, git index와 원래 main은 변경하지 않는다.

남은 네이티브 검증을 위한 [임시 workflow 초안](korea-v4-native-validation.yml)은 `docs/`에 있는 비활성 문서다. 승인 후에만 검증 브랜치 `verify/korea-v4-20261029`의 `.github/workflows/`로 옮길 수 있다. Rust 1.99.1, 프로젝트의 네 OS/아키텍처, release build·tests·지원되는 독립 CLI 경로를 명시한다. 기존 영구 workflow와 Nu 검사 정책을 바꾸지 않는다. Draft PR과 이 검증 브랜치의 실행을 승인받더라도 main 병합이나 배포까지 승인된 것으로 확대하지 않는다.
